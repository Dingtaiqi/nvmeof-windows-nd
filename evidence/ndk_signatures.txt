IMPORTANT - THE NAMES IN THE TASK AND THE INSTALLED HEADER DO NOT FULLY MATCH
----------------------------------------------------------------------------
Two of the four requested symbols do not exist in this header at all:

  - NDK_FN_CREATE_CONNECTION_REQUEST : no hit in ndkpi.h (or anywhere under
    the 10.0.26100.0 Include tree).
  - NdkAcceptConnection              : no hit in ndkpi.h.

This header is the NDKPI 2.0 interface. Its listener callback is
NDK_FN_CONNECT_EVENT_CALLBACK (VOID, two parameters, NO out-parameter), and
acceptance is NDK_FN_ACCEPT / NdkAccept (it needs a QP and an async
completion). There is also no NdkGetListenerDispatch function: the dispatch
table hangs directly off NDK_LISTENER.Dispatch.

The code added to nvmeofk.c therefore uses ONLY the declarations quoted below.
Nothing here is reconstructed from memory. The protocol-visible values and
object lifetimes still follow the existing, already-working nvmeofk.c code.

[2] NDK_FN_CREATE_CONNECTION_REQUEST
------------------------------------
NOT PRESENT in this header. The installed callback type is
NDK_FN_CONNECT_EVENT_CALLBACK, ndkpi.h lines 807-813:

typedef
_IRQL_requires_max_(DISPATCH_LEVEL)
VOID
(*NDK_FN_CONNECT_EVENT_CALLBACK) (
    _In_opt_ PVOID ConnectEventContext,
    _In_ NDK_CONNECTOR *pNdkConnector
    );

Answer to the specific question asked: the old NDKPI 1.x
NDK_FN_CREATE_CONNECTION_REQUEST did have a PVOID * out-parameter; the
installed NDKPI 2.0 callback does NOT. It returns VOID and has exactly two
parameters. The accept/reject decision is a separate call on the connector
(see [3]).

Consequence: the compiler-checked forward declaration used in the code is

    static NDK_FN_CONNECT_EVENT_CALLBACK MyCreateConnectionRequest;

and the definition must be

    static VOID MyCreateConnectionRequest(PVOID ConnectEventContext,
                                         NDK_CONNECTOR *pNdkConnector)
