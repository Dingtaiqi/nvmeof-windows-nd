# Reconnect works; the resent capsule then gets no response

Run after the fix, with the device freshly loaded at boot (device OK / CM_PROB_NONE).

The idle timeout fired as designed and the driver handled it correctly:

  send #218 len=72 ... t=222910ms callSt=0x00000103 irpSt=0xC000020D info=0 irpOut=1
  send: the socket is gone (0xC000020D STATUS_CONNECTION_RESET, info=0); the capsule was
        not transmitted, so the connection is re-established and it is sent again
  === reconnect: rebuilding connection to 127.0.0.1:4421 ===
  handshake: ICReq sent (128 bytes, cpda=4 dgst=0 maxr2t=0)
  handshake OK: peer pfv=0 cpda=4 dgst=0 maxr2t=0
  reconnect: connection is up again (1 reconnects on this connection)

Every diagnostic in that sequence is right: the status is finally named correctly,
Information=0 correctly proves the capsule never reached the wire so resending it is
safe, and the reconnect completes its handshake.

But the log ends there. There is no resp line for cid=218, and the disk stays RAW:

  Disk5  RAW  Online  (16 MiB)
  diskpart select/clean/convert/create hung for 240 s with only its banner printed

So the resend either does not happen or its response is never read. The next step is
one question, asked of the code: after NvtcpkReconnect returns, does the caller actually
call NvtcpkSend again, and does the receive side use a reset offset? A receive offset
left over from the dead connection would wait forever for bytes at an offset the new
connection will never reach - and no timeout would fire, because the receive itself
has a 30 s bound only if it is entered at all.

Nothing crashed. Both drivers stayed Running, the network stayed up, and no dump was
written, so this is a logic gap rather than a stability problem.
